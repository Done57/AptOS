## 二、怎么构建和运行

```bash
source /tmp/tcenv.sh          # 每个新 shell 都要，nasm 和交叉工具链在这

make                          # 32 位系统（默认，完整可用）
make kernel64                 # 64 位内核
make img64                    # 64 位可启动镜像 build/os64.img

# 跑 64 位（直接用 make img64 的产物即可）
qemu-system-x86_64 -m 256 -vga std -L /tmp/tc/root/usr/share/qemu \
    -drive file=build/os64.img,format=raw,index=0,media=disk \
    -display none -serial file:/tmp/s.log -no-reboot

# 手动做 64 位镜像时必须带 --kernel64（stage2 据此进长模式）

    --stage1 build/stage1.bin --stage2 build/stage2.bin \
    --kernel build/kernel64.bin --size-mb 8
qemu-system-x86_64 -m 256 -vga std -L /tmp/tc/root/usr/share/qemu \
    -drive file=/tmp/lm64.img,format=raw,index=0,media=disk \
```

## 三、踩过的坑（都是静默失败型，值得记住）

### 1. 必须用 qemu-system-x86_64

`qemu-system-i386` **根本不支持长模式**，换 CPU 型号也没用：

```
qemu-system-i386  + qemu64:  CPUID EDX = 0x0193fbfd   LM 位 = 0
qemu-system-x86_64:          CPUID EDX = 0x2193fbfd   LM 位 = 1
```

它不报错，只是让你的 `wrmsr`（写 EFER.LME）石沉大海，回读永远是 0。
**排查建议**：先查 CPUID 0x80000001 的 EDX bit 29。

### 2. 进长模式的顺序是硬性的

```
建4级页表 → 载入CR3 → 置CR4.PAE(bit5) → 置EFER.LME(bit8) → 置CR0.PG(bit31) → 远跳
```

`EFER.LME=0` 就开 `CR0.PG` 会进普通 32 位分页，不是长模式。

### 3. 16 位代码里跳 32 位段，远跳必须用 dword

```asm
jmp dword 0x08:pm_entry     ; 正确，7 字节
jmp 0x08:pm_entry           ; 错误，nasm 编成 5 字节 16 位远跳
```

后者会把选择子折进偏移，跳过去用空选择子 → `#GP`。

### 4. 64 位代码段描述符的 L 位

```
0x00AF9A000000FFFF
  Access=0x9A  Flags=0xA0 → G=1, D/B=0, L=1 ✓
```

`L` 是 Flags 字节的 bit5（不是 bit6）。`0x20` 也能用（G=0，64 位段不检查限长）。

### 5. 不要用 16 位寄存器搬内存到 1MB

`mov esi, 0x20000` 在 16 位模式下会被截断成 0。而且 16 位 `rep movsb`
用的是 `SI/DI/CX` 不是 `ESI/EDI/ECX`。

**解法**：把搬迁**推迟到 32 位保护模式之后**，那时有完整 32 位寄存器和
4GB 平坦寻址，一条 `rep movsb` 就够。

### 6. int 13h 扩展读不能跨 64KB 边界

跨段尾会回绕到段首、覆盖已读数据。每批扇区数要按
`(0x10000 - offset) >> 9` 限制。

**还有**：`0x10000` 放不进 16 位寄存器，`dst_off == 0` 时要单独处理
（否则算出 0 → 判定"本段已满" → 无限循环，一个字节没读）。

### 7. BIOS 读盘不要直接读 1MB

实测直接让 `int 13h` 读到 `0x100000` 会**静默失败**（内存里全是 0）。
改成先读到低内存 `0x20000`，进保护模式后再搬。

### 8. %x 在 64 位下只打 32 位

`util.c` 的 `fmt_uint` 原来收 `u32`，64 位地址会被截断。
而且 C 变参语义要求**格式串匹配参数类型**：

- `%x` → 读 `unsigned int`（4 字节）
- `%lx` → 读 `unsigned long`（64 位平台是 8 字节）

**打 64 位值必须用 `%lx`**，否则取参时就只读 4 字节了，转换类型没用。
`%p` 已改成自动打满宽度。

### 9. size_t 必须是 8 字节

`types.h` 原来是 `typedef u32 size_t`。64 位下这会让所有指针运算截断。
已改成按平台切换，并加了 `uptr`/`sptr`。

### 10. pushfl/popfl 是 32 位指令

`io.h` 的 `irq_save`/`irq_restore` 在长模式下要用 `pushfq`/`popfq`。

### 11. 32 位下 u64 除法会引入 __udivmoddi4（阶段二回归）

`fmt_uint` 改成收 `u64` 后，32 位平台没有 64 位除法指令，
编译器生成对 libgcc `__udivmoddi4` 的调用，而内核不链 libgcc ——
**链接期才炸**，编译期毫无征兆。

修法：`fmt_uint` 内部按平台用 `fmt_val_t`（64 位=u64，32 位=u32），
64 位值只在 64 位构建里真正按 64 位处理。

**教训：改了共享代码，两个平台都要重新链接一遍，只 make 不够。**

### 12. add 溢出进位被无视 → 大内核必坏（最隐蔽）

stage2 读盘推进逻辑原来是：

```asm
add     [dst_off], ax          ; 0xC000 + 0x4000 回绕成 0x0000
cmp     word [dst_off], 0xFF00
jb      .noadv                 ; 判定"离边界还远"→ 不进段！
```

`add` 跨过 64KB 时 CF=1，但代码只看 cmp —— 回绕成 0 后下一批
写到段首**覆盖已读数据**。内核超过 64KB（32 位内核 158KB/309 扇区）
从第 128 扇区起全是坏的，表现为跳进内核后 `#GP` → 双重错误。

64 位内核一直只有 10~33 扇区、单批读完，从没触发 ——
**是 32 位大内核第一次踩中**。

修法：`add` 后紧跟 `jc .segadv` 显式处理进位；CHS 路径同样补上。

**教训：小内核测试通过 ≠ 读盘逻辑正确，必须用大内核验证。**

### 14. 长模式不会自动开中断（sti 缺失，中断静默丢失）

idt64_init 做完 lidt + PIC 重映射后 IF 仍是 0 —— 32 位路径里
这一步隐含在别处，64 位把每一环写明白时就漏了它。症状非常迷惑：
- QEMU `-d int` 日志里 **64 位阶段一个中断事件都没有**（不是死在
  处理程序里，是 CPU 根本不理 PIC）；
- `hlt` 永远等不到 tick，内核像挂了一样。

修法：lidt 之后显式 `sti`。验证手段：`pushfq` 读 EFLAGS.IF。

**教训："中断没反应"先查 IF，再查 IDT 格式 —— 顺序反了会白查半天。**

### 15. qemu monitor 与 -d int 日志不能混用（日志变空）

`-monitor stdio`（管道喂 sendkey）和 `-d int -D file` 同时用时，
中断日志会整个变空。要用 sendkey 又要抓中断日志：
`-monitor unix:/tmp/mon.sock,server,nowait` + socket 发键。

### 13. stage2 是共享的，改它等于同时改两个系统

stage2 加了长模式路径后，32 位镜像也被带进长模式（它还是 32 位代码，
进去就死）。现在 stage2 用一个补丁字节 `long_mode` 分岔：
`mkimg.py --kernel64` 写 1（搬 1MB + 进长模式），默认写 0
（搬 64KB + 直接跳）。**镜像过期也是坑**：mkimg 用了旧 stage2.bin，
表现为补丁偏移对不上 —— 重建镜像前先确认 stage2.bin 是新的。

## 五、阶段三要做什么

按依赖顺序：

1. **中断/IDT 64 位化** —— 64 位 IDT 门、`iretq`、寄存器压栈顺序全变。
   现在 64 位内核是 `cli` 状态，开了中断立刻崩。
2. **物理内存管理 + 堆** —— `paging.c`/`heap.c` 迁过来，
   把 `paging64.c` 里那个临时的 bump 分配器换成正式的。
3. **ring3 用户态 + 系统调用** —— `usermode.asm`、`syscall.c`。
4. **图形栈** —— `gfx.c`/`gui.c`，之后才有画面。
5. **用户程序** —— `apps/lib/*` 和 20 个程序。

## 六、已知的设计债

- `paging64.c` 的页表池是**临时 bump 分配器**（16MB~32MB），
  物理内存管理就绪后要换掉。
- 页表池只有 16MB，约 4096 张页表，够用但不是长久之计。
- `console_pump()` 在 64 位下是**空实现**（图形栈没来），
  所以 `klog_screen(1)` 在 64 位下无效，日志只走串口。
- 64 位内核只恒等映射了前 1GB。

## 附：ISO 安装盘引导修复（踩坑 #26）

| # | 坑 | 教训 |
|---|---|---|
| 26 | `boot/stage1.asm` 与 `boot/stage2.asm` 的 `lba_to_chs` 里，算完柱面后第二段用 `mov ecx, SPT` 重设除数，**把 CH 中刚存好的柱面号一起清成了 0** | 16 位 BIOS CHS 读取会永远读柱面 0。软盘引导时 stage2 读内核（LBA 9 起 354 扇区）越过柱面 0 后全是错数据：前 27 扇区碰巧正确，所以 entry 能跑、kmain 是垃圾——表现为"进内核就跳飞"。硬盘引导走 DAP(int 13h 42h) 不碰 CHS，所以一直没暴露。修法：柱面暂存到内存变量 `chs_cyl`，除数改用 EDI（**不能**用 ESI/EDI 之外的寄存器——stage1 的 DI 是目标段、stage2 的 BX 是目标偏移） |
